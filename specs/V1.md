# Spec: Missing Utils v1 Foundation

**Author:** ads-missing-utils maintainers

**Date:** 2026-08-04

**Status:** Approved

**Reviewers:** Repository owner

**Related document:** [PROJECT_PLAN.md](../PROJECT_PLAN.md)

## Context

The repository currently contains a product plan for a broad DevOps and security toolkit but no runnable software. The plan intentionally spans 24 utilities and several platform-specific diagnostic domains. Implementing all of them as a first release would leave command contracts, test coverage, packaging, and security behavior unproven.

This release establishes the toolkit's executable foundation with three independent, cross-platform file and configuration utilities: `jwalk`, `envsub`, and `hashsum`. They exercise the shared CLI, versioned structured output, error, redaction, and release conventions before the Linux-specific diagnostics and automation adapters are built.

The release is intended for operators and CI jobs that need deterministic structured output without parsing human-oriented shell command output. It must be safe by default: it may read inputs and write only explicitly requested output files, never evaluate shell fragments, and never print secret values in diagnostics.

## Functional Requirements

### Shared command contract

- FR-1: Each v1 command MUST expose `--help`, `--version`, `--format json|ndjson`, `--no-color`, and stable exit codes 0, 1, 2, 3, 4, and 124 as defined in the project plan.
- FR-2: In `json` or `ndjson` mode, each v1 command MUST write machine-readable records only to stdout and MUST write diagnostics only to stderr.
- FR-3: Each structured record MUST include a v1 schema identifier and MUST use an explicit `status` or `outcome` value for non-success observations.
- FR-4: Each v1 command MUST reject invalid flags and malformed input with exit code 2 and a concise stderr diagnostic.

### `jwalk`

- FR-5: `jwalk` MUST recursively traverse one or more explicitly supplied root paths and emit a record for every matching entry.
- FR-6: `jwalk` MUST support filters for entry type, include regular expression, exclude regular expression, minimum size, maximum size, older-than duration, and newer-than duration.
- FR-7: `jwalk` MUST emit `path`, `relative_path`, `type`, `size`, `mtime`, `mode`, `uid`, `gid`, `inode`, and `device` when the operating system provides the value; unavailable values MUST be `null`.
- FR-8: `jwalk` MUST default to not following symlinks, MUST avoid traversal cycles, and MUST support an explicit `--follow-symlinks` option.
- FR-9: `jwalk` MUST emit an error record for an entry that cannot be read and continue unless `--fail-on-error` is specified.
- FR-10: `jwalk` MUST provide lexicographically deterministic records by default for a fixed filesystem snapshot.

### `envsub`

- FR-11: `envsub` MUST replace `${NAME}` and `${NAME:-default}` placeholders without executing shell syntax, recursive expansion, command substitution, or arithmetic expansion.
- FR-12: `envsub` MUST load values from process environment, repeated `.env` files, and repeated `--set NAME=value` flags using documented precedence: `--set` highest, process environment next, then later `.env` files over earlier `.env` files.
- FR-13: `envsub` MUST fail when a referenced variable is unset and has no placeholder default or schema default.
- FR-14: `envsub` MUST support a YAML schema with string, integer, number, boolean, enum, URL, duration, byte-size, and JSON value types.
- FR-15: `envsub` MUST validate every supplied or defaulted schema value before rendering and MUST reject unknown schema keys when `--strict-schema` is set.
- FR-16: `envsub` MUST mark schema-declared secrets and MUST mask their values in diagnostics, explain output, and errors.
- FR-17: `envsub` MUST support `--check`, `--list-keys`, and `--explain`; these modes MUST NOT write a rendered output file.
- FR-18: When `--output` is supplied, `envsub` MUST write via a same-directory temporary file and atomic rename, preserving the existing destination mode when it exists.

### `hashsum`

- FR-19: `hashsum create` MUST calculate SHA-256 and BLAKE3 for each requested regular file from one file read per file.
- FR-20: `hashsum create` MUST accept paths as arguments and `jwalk` NDJSON records through `--from-jwalk`.
- FR-21: `hashsum create` MUST generate a versioned JSON manifest sorted by normalized root-relative path, including each file's size, modification time, selected algorithms, digest values, and stable/unstable status.
- FR-22: `hashsum create` MUST detect observable changes to a file during hashing and mark its record `unstable` rather than reporting it as stable.
- FR-23: `hashsum verify` MUST reject manifest paths that are absolute, empty, duplicate after normalization, or escape `--root`.
- FR-24: `hashsum verify` MUST report missing, changed, unreadable, unstable, and unexpected files as separate result classes and exit 1 if any required file does not verify.
- FR-25: `hashsum` MUST hash files with a bounded worker pool, support `--workers`, and update all selected algorithms from a single input stream.
- FR-26: `hashsum` MUST send progress only to stderr and only when `--progress` is explicitly selected.

### Tooling and delivery

- FR-27: The repository MUST build all three commands from one Go module and MUST provide `make test`, `make build`, and `make check` targets.
- FR-28: The repository MUST include JSON Schema documents for v1 shared responses, `jwalk` records, `envsub` responses, and `hashsum` manifests.
- FR-29: The repository MUST include continuous-integration workflows that run formatting, static analysis, unit tests, and a multi-platform build matrix for Linux, macOS, and Windows.
- FR-30: The repository MUST include reproducible archive-release configuration that emits checksums and SBOM metadata when a version tag is released.

## Non-Functional Requirements

- NFR-P1: `jwalk` MUST traverse and encode metadata for 10,000 regular files in a test fixture within 10 seconds on the CI Linux runner.
- NFR-P2: `hashsum` MUST use no more than `workers + 2` open input file descriptors while hashing independent files, excluding standard streams.
- NFR-P3: `envsub` MUST render a 1 MiB template with 1,000 placeholders within 2 seconds on the CI Linux runner.
- NFR-S1: `envsub` MUST NOT execute template content or log a schema-declared secret value in any success or failure path.
- NFR-S2: `hashsum verify` MUST resolve each manifest path beneath the canonical `--root` directory before opening it.
- NFR-R1: All output-file writes MUST either leave the prior destination intact or replace it with a complete new file; partial destination files are prohibited.
- NFR-R2: Every command MUST return within 2 seconds after a cancelled context or closed stdout pipe when its current filesystem operation completes.
- NFR-C1: v1 command and schema identifiers MUST remain compatible for all v1 patch releases; breaking changes require a new major schema identifier.

## Acceptance Criteria

### AC-1: Shared structured output discipline (FR-1, FR-2, FR-3, FR-4)

Given any v1 command is invoked with `--format json`

When the operation succeeds or fails due to invalid input

Then stdout contains only one valid JSON document on success

And stderr contains no structured success record

And invalid input exits with code 2.

### AC-2: `jwalk` filters and metadata (FR-5, FR-6, FR-7, FR-10, NFR-P1)

Given a fixture tree containing files with distinct names, types, sizes, and modification times

When `jwalk` runs with combined type, regex, size, and age filters

Then it emits only matching entries in lexical path order

And every successful record validates against the `missing-utils/jwalk/v1` schema.

### AC-3: `jwalk` symlink and error behavior (FR-8, FR-9)

Given a fixture tree with a symlink cycle and an unreadable child directory

When `jwalk` runs without `--follow-symlinks`

Then it completes without descending through the symlink

And it emits an error record for the unreadable child when the platform permits the fixture

And `--fail-on-error` exits with code 3.

### AC-4: `envsub` precedence and defaults (FR-11, FR-12, FR-13)

Given a template with required, placeholder-defaulted, and schema-defaulted variables

When values are provided by `.env`, process environment, and `--set`

Then the rendered result uses the documented precedence

And missing required variables cause no output file to be written.

### AC-5: `envsub` validation and secret redaction (FR-14, FR-15, FR-16, NFR-S1)

Given a schema with integer, enum, URL, and secret fields

When an invalid value or an unset secret is supplied

Then the command exits with code 2

And diagnostics identify the key and validation failure

And diagnostics do not contain the secret value.

### AC-6: `envsub` non-writing modes and atomic output (FR-17, FR-18, NFR-R1)

Given an existing destination file and a valid template

When `envsub --check`, `--list-keys`, or `--explain` is used

Then the destination remains unchanged

And when a render succeeds the destination is atomically replaced

And when rendering fails the destination remains byte-for-byte unchanged.

### AC-7: `hashsum` create manifest (FR-19, FR-20, FR-21, FR-25, FR-26)

Given a `jwalk` NDJSON stream describing regular files

When `hashsum create --from-jwalk --workers 2` runs

Then it creates a sorted versioned manifest containing matching SHA-256 and BLAKE3 digests

And the command reads each file once while updating both digests

And progress, when selected, appears only on stderr.

### AC-8: `hashsum` in-flight modification handling (FR-22)

Given a file whose size or modification time changes between the pre-hash and post-hash observations

When `hashsum create` hashes the file

Then its manifest record has status `unstable`

And the command does not label the record `stable`.

### AC-9: `hashsum` verification and path safety (FR-23, FR-24, NFR-S2)

Given a manifest containing one valid file, one modified file, one missing file, and one path escaping the root

When `hashsum verify --root fixture manifest.json` runs

Then it emits a separate result for each class

And it never opens a path outside `fixture`

And it exits with code 1.

### AC-10: Build, schemas, and release tooling (FR-27, FR-28, FR-29, FR-30)

Given a clean checkout with supported Go installed

When `make check`, `make test`, and `make build` run

Then all commands complete successfully

And schemas and release configuration are present

And CI defines Linux, macOS, and Windows build jobs.

## Edge Cases

- EC-1: A `jwalk` root does not exist -> emit a structured error and exit 2 without emitting matching-entry records.
- EC-2: A `jwalk` regular expression is invalid -> reject it before traversal with exit 2 and a diagnostic naming the flag.
- EC-3: A `jwalk` entry disappears after discovery -> emit an error record, continue by default, and exit 3 under `--fail-on-error`.
- EC-4: An `envsub` placeholder has an unsupported operator such as `${A:?error}` -> reject the template with exit 2; do not render partial output.
- EC-5: An `.env` line is malformed, duplicated, or contains a comment -> reject malformed lines, use the later value for duplicates in the same source, and ignore blank/comment lines.
- EC-6: An `envsub` output path has no writable parent -> return exit 4 and leave any existing destination unchanged.
- EC-7: A schema-declared integer receives `1.2` or `true` -> reject it with exit 2 and redact it if the field is secret.
- EC-8: `hashsum create` receives a directory, symlink, FIFO, or unreadable file -> emit an error record; do not open special files; return exit 1 after processing other inputs.
- EC-9: A `jwalk` NDJSON input record is malformed or lacks a non-empty `path` -> reject input with exit 2 before writing a manifest.
- EC-10: A manifest declares an unknown digest algorithm -> reject verification with exit 2.
- EC-11: A manifest includes duplicate paths after slash normalization -> reject verification with exit 2.
- EC-12: A manifest file is syntactically valid but exceeds a 64 MiB input limit -> reject it with exit 2 without allocating unbounded memory.

## API Contracts

All commands are local CLI APIs. The following JSON types describe their structured contracts.

```typescript
type ExitCode = 0 | 1 | 2 | 3 | 4 | 124;
type ObservationStatus = "ok" | "error" | "stable" | "unstable" | "missing" | "changed" | "unreadable" | "unexpected";

interface Diagnostic {
  code: string;
  message: string;
  path?: string;
  field?: string;
}

interface CommandResponse<T> {
  schema: "missing-utils/response/v1";
  command: "jwalk" | "envsub" | "hashsum";
  outcome: "pass" | "fail" | "partial" | "error";
  data: T;
  diagnostics: Diagnostic[];
}

interface JwalkRecord {
  schema: "missing-utils/jwalk/v1";
  status: "ok" | "error";
  path: string;
  relative_path: string | null;
  type: "file" | "directory" | "symlink" | "other" | null;
  size: number | null;
  mtime: string | null;
  mode: string | null;
  uid: number | null;
  gid: number | null;
  inode: number | null;
  device: number | null;
  error?: Diagnostic;
}

interface EnvsubSchemaField {
  type: "string" | "integer" | "number" | "boolean" | "enum" | "url" | "duration" | "byte-size" | "json";
  default?: string | number | boolean | object | array;
  values?: Array<string | number | boolean>;
  secret?: boolean;
  optional?: boolean;
}

interface HashManifest {
  schema: "missing-utils/hashsum/v1";
  algorithms: Array<"sha256" | "blake3">;
  root: string;
  files: HashManifestFile[];
}

interface HashManifestFile {
  path: string;
  size: number;
  mtime: string;
  status: "stable" | "unstable";
  digests: { sha256?: string; blake3?: string };
}

interface VerificationRecord {
  schema: "missing-utils/hashsum-verify/v1";
  path: string;
  status: "ok" | "missing" | "changed" | "unstable" | "unreadable" | "unexpected" | "error";
  diagnostics?: Diagnostic[];
}
```

## Data Models

### CLI result envelope

| Field | Type | Constraints |
|---|---|---|
| schema | string | Exact v1 schema identifier |
| command | string | `jwalk`, `envsub`, or `hashsum` |
| outcome | string | `pass`, `fail`, `partial`, or `error` |
| data | object or array | Command-specific, JSON-serializable |
| diagnostics | array | Zero or more redacted diagnostics |

### Environment field definition

| Field | Type | Constraints |
|---|---|---|
| name | string | Environment identifier; unique within schema |
| type | string | One supported `envsub` type |
| default | scalar/object/array | Optional; validates against type |
| values | array | Required only for `enum` |
| secret | boolean | Defaults false; masks diagnostics when true |
| optional | boolean | Defaults false; allows absence |

### Hash manifest file

| Field | Type | Constraints |
|---|---|---|
| path | string | Non-empty normalized relative path; unique |
| size | unsigned integer | Observed pre-hash size |
| mtime | RFC 3339 string | Observed pre-hash modification time |
| status | enum | `stable` or `unstable` |
| digests | object | At least one supported algorithm with lowercase hex digest |

## Out of Scope

- OS-1: The remaining 21 planned utilities, including `ports`, `pwatch`, `tfchanges`, `spacelift-helper`, and `regocheck` — they depend on the v1 command, schema, and release conventions.
- OS-2: Linux-only kernel inspection, network namespace analysis, eBPF collection, package-manager integration, and LSM reasoning — separate platform-specific specifications are required.
- OS-3: A background agent, daemon, database, web UI, telemetry service, or SaaS control plane — v1 consists solely of local binaries and repository automation.
- OS-4: Remote secret-manager lookups, command evaluation in templates, or secret encryption — these introduce network, credential, and threat-model requirements outside v1.
- OS-5: Manifest signing, transparency logs, Merkle/chunked manifests, remote storage, and resumable hash caches — these are later `hashsum` extensions.
- OS-6: Fully identical filesystem metadata across operating systems — unsupported metadata is represented as `null` rather than synthesized.
